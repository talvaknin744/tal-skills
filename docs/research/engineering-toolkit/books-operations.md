**Infrastructure:** Chapter 1 supports making small, independently testable infrastructure changes through versioned code. Infrastructure design must serve actual workload requirements. It does not supply detailed Terraform failure handling. Use the book for the delivery model and current provider documentation for execution behavior. [Author edition page](https://infrastructure-as-code.com/book/), [official chapter](https://www.thoughtworks.com/content/dam/thoughtworks/documents/books/infra-as-code-3e-free-chapter.pdf), [publisher](https://www.oreilly.com/library/view/infrastructure-as-code/9781098150341/)

**Integration:** EIP provides a useful vocabulary for selecting integration styles and separating transport adaptation from application behavior. Messaging trades temporal coupling for asynchronous failure and observation work; it is not automatically the best choice for a local operation. Its old JMS/.NET examples are illustrative rather than production templates. [Official samples](https://www.enterpriseintegrationpatterns.com/downloads.html), [publisher sample](https://ptgmedia.pearsoncmg.com/images/9780321200686/samplepages/0321200683.pdf), [Message Endpoint chapter](https://www.enterpriseintegrationpatterns.com/docs/EnterpriseIntegrationPatterns_HohpeWoolf_ch03.pdf), [author caveat](https://www.enterpriseintegrationpatterns.com/patterns/messaging/Introduction.html)

**Event streams:** Stopford connects ownership, projection rebuilding, transaction boundaries, and schema evolution. A retained log can support rebuilding derived state, but feasibility depends on available history and recovery duration. Read the transaction guarantee together with its external-system limitation. Modern defaults and format-specific compatibility must be checked separately. [Author's complete book](https://benstopford.com/uploads/Designing-Event-Driven-Systems.pdf)

## Corrections required before turning books into instructions

The following are current runtime checks and engineering applications, not additional claims attributed to the books.

- **Kafka:** atomically committing output records and consumed offsets can protect a Kafka processing boundary. An external HTTP effect or database write is outside that transaction. A consumer must not expose aborted records; track actual isolation, offset management, producer identity, and rebalance handling. Stopford's 2018 restriction on consumer-group support is historical. Test a crash after an external effect but before offset commit. [Kafka 4.1 design](https://kafka.apache.org/41/design/design/)
- **Schemas:** an additive field is not universally compatible; defaults and the schema format matter. Confluent's default `BACKWARD` checks the immediately preceding version, not every retained version. Test the actual oldest replayed data and deployed reader/writer combinations. Schema acceptance does not prove business meaning. [Current compatibility rules](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)
- **Registry enforcement:** the book's description of checking every message is too broad. Identify the configured serializer and any broker-side validation; merely having a registry is insufficient. Confluent's broker validation checks schema identification rather than validating every payload against its schema. [Serialization configuration](https://docs.confluent.io/platform/current/schema-registry/fundamentals/serdes-develop/overview.html), [broker-side validation](https://docs.confluent.io/platform/current/schema-registry/schema-validation.html)
- **Acknowledgements:** publisher confirmation and consumer acknowledgement protect different RabbitMQ boundaries. Neither establishes a database-plus-broker transaction. Lost confirmation can require retransmission and therefore duplicate handling. Test publication acknowledgement loss separately from consumer acknowledgement loss. [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms), [reliability guide](https://www.rabbitmq.com/docs/reliability)
- **Infrastructure:** a speculative plan can become outdated; check the final plan and preserve state locking. Apply can partially succeed without automatic rollback. A previous state file is not a reverse migration. After failure, inspect actual resources and state, then produce a repair plan. `prevent_destroy` is conditional protection: removing the resource configuration removes that guard. Saved plans may contain secrets. [Lifecycle reference](https://developer.hashicorp.com/terraform/language/meta-arguments/lifecycle), [Plan reference](https://developer.hashicorp.com/terraform/cli/commands/plan), [locking](https://developer.hashicorp.com/terraform/language/state/locking), [apply failures](https://developer.hashicorp.com/terraform/tutorials/cli/apply)

## Extend existing recovery research

Re-read SRE Chapter 26's recovery rehearsal and independent validation sections, plus Workbook Chapter 16's noninteractive canary section. Recovery acceptance must include usable application data, elapsed recovery time, available dependencies, and reconciled cross-store relationships. A long-job canary needs evidence across a complete work unit, with canary/control attribution preserved. These findings extend the existing [SRE notes](../sre-reliability-reading.md). [Data integrity](https://sre.google/sre-book/data-integrity/), [canarying](https://sre.google/workbook/canarying-releases/)

For PostgreSQL, a successful `pg_verifybackup` is not a successful restore rehearsal. Version-matched WAL checking, the required WAL chain, configuration, and application access require separate consideration. A backup may be valid yet fail the recovery target because the needed log history or non-WAL configuration is missing. [PostgreSQL 18 verification](https://www.postgresql.org/docs/18/app-pgverifybackup.html), [PITR](https://www.postgresql.org/docs/18/continuous-archiving.html)

Reuse the prior [DDIA processing reading](../ddia-processing-recovery.md) for replay identity and retained input history, preserving its explicit **early-release draft** provenance. ## Recommended use in the toolkit

1. `messaging-reliability`: record effect, publication, acknowledgement, replay, ordering, and schema boundaries before selecting a pattern. Include two distinct acknowledgement-loss cases and a historical-schema replay case.
2. `infrastructure-change-safety`: inspect the target and proposed replacement/destruction, bind evidence to the actual change, and define partial-failure recovery. Exercise a disposable partial apply; never infer successful repair from restored state metadata alone.
3. `recovery-validation`: recover into an isolated target, verify business invariants and access, and measure recovery objectives. Include unavailable keys/configuration, missing history, and a restore that passes file checks but fails application use.
4. Specialist agents should retrieve these skills conditionally. Give one agent ownership of overlapping infrastructure files and another responsibility for independent failure review; adding more agents does not establish the runtime guarantees.

An especially relevant experienced-practitioner follow-up is Morris's 2026 account of using infrastructure code as a stable basis for coding agents. It is a personal engineering report, not a controlled effectiveness study. Its useful application here is to have agents modify reviewable infrastructure definitions and retain the delivery checks around execution. [Author's account](https://infrastructure-as-code.com/posts/why-i-use-infra-code-with-agents.html)
