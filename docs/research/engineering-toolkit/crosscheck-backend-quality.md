## Required correction

**The Tailscale verification criterion needs two distinct outcomes.** `quality-tailscale-resource-ownership.practice.verification` currently expects prompt rejection with both empty and warm caches. Its own counterexample correctly acknowledges that cached certificates bypass `HostPolicy`. Current autocert documentation confirms this and separately states that the HTTP fallback is not protected by `HostPolicy`. Changing certificate acquisition policy therefore cannot prove endpoint retirement. [autocert Manager](https://pkg.go.dev/golang.org/x/crypto/acme/autocert#Manager)

Suggested replacement: “With an empty cache, verify that the retired hostname cannot initiate certificate acquisition and that resource usage remains bounded. With a warm cache, verify the documented cached-certificate behavior. If the requirement is to reject all retired-host traffic, verify a separate host/routing policy under both cache states.” This prevents a cleanup agent from silently expanding a resource-ownership fix into an access-control change. The incident's DNS and cache-expiry explanations are explicitly hypotheses, which the quality lane already preserves. [Tailscale incident](https://tailscale.com/blog/case-of-spiky-file-descriptors)

## Mixed-version application and schema migration evidence

The following separates tool behavior from the application compatibility rules inferred for this repository.

**gh-ost:** Reviewed documentation at commit `f7a42f6b8028e96d3c8abd47a4da38baedb1161d`, resolved from upstream master during this research. The documented atomic cutover briefly blocks pending connections; a failed cutover leaves the original table available. That table-level property does not establish compatibility with every application version. Check tool-specific requirements before proposing it: supported topology, shared non-null migration key, row-based binlog settings, and unsupported foreign keys/triggers. A source commit pin is not evidence that the tool was installed or executed. [Cutover](https://github.com/github/gh-ost/blob/f7a42f6b8028e96d3c8abd47a4da38baedb1161d/doc/cut-over.md), [requirements](https://github.com/github/gh-ost/blob/f7a42f6b8028e96d3c8abd47a4da38baedb1161d/doc/requirements-and-limitations.md)

**Vitess 24.0, labelled stable by the site:** `COMPLETE` permits a postponed migration to proceed; it is not synchronous confirmation. The documented shard canary is unsafe for adding/removing columns when shards then expose inconsistent schemas. For applicable Online DDL, VDiff requires postponed completion and `ready_to_complete=1`. Application readiness must wait for observed completion on every required shard and must tolerate the transition. [Postponed migrations](https://vitess.io/docs/24.0/user-guides/schema-changes/postponed-migrations/), [VDiff validation](https://vitess.io/docs/24.0/user-guides/schema-changes/validating-migrations/)

**Rollback is conditional:** Vitess documents last-successful-migration restrictions and examples where later data no longer fits the old type or uniqueness constraint. Its revert page says 24 hours, while the newer flags page provides retention overrides; do not hardcode a universal rollback window from the former. Confirm deployed-version behavior, actual retained artifacts, configured retention, strategy, and data representability. Some instant-DDL paths do not retain a shadow table for reversion. This documentation tension is recorded, not resolved by an invented guarantee. [Revertible migrations](https://vitess.io/docs/24.0/user-guides/schema-changes/revertible-migrations/), [strategy flags](https://vitess.io/docs/24.0/user-guides/schema-changes/ddl-strategy-flags/)

**Stripe's historical database case study (2017-02-02):** The useful pattern is staged dual writes, verified read migration, write-path migration, then removing the old representation after its consumers are gone. Shadow comparisons and complete backfill enumeration provide different evidence. The article does not specify a complete concurrency or cross-store atomicity protocol; copying its sequence alone cannot prevent a stale backfill overwrite or interrupted dual write. Those are additional design obligations. [Online migrations at scale](https://stripe.com/blog/online-migrations)

**Current Stripe integration guidance:** Pin the API contract appropriate to the SDK and separately account for event-destination versions. During an endpoint migration, multiple destinations can deliver the same subscribed events. Planned ignoring of a migration copy and retrying the old route for rollback have specific documented purposes; they are not general policies to acknowledge malformed events or retry all client errors. [Upgrade your integration](https://docs.stripe.com/upgrades)

## Proposed skill changes

Extend existing boundaries/consistency guidance and new `infrastructure-change-safety`; do not create another generic architecture skill.

1. **Trigger:** application rollout and schema/data changes overlap. **Failure:** an old process, long-running job, queued retry, consumer, or rollback binary encounters an incompatible schema. **Mechanism:** record read/write requirements for every admitted version; expand, migrate, verify, retire consumers, then contract. **Limit:** a coordinated maintenance window can use a simpler plan. **Counterexample:** all pods are new while an old queued job still requires the removed field. **Verification:** execute the version/schema matrix and reject contraction until every remaining consumer is compatible.
2. **Trigger:** backfill runs alongside writes. **Failure:** an old snapshot overwrites newer target data, or a crash splits a dual write. **Mechanism:** choose an authority and an atomic transaction or durable change-intent protocol, then apply a justified ordering/conditional-update rule. **Limit:** the revision model below assumes a monotonic per-record revision; multiple independent authorities need conflict rules. **Counterexample:** wall-clock timestamps are not automatically a total order. **Verification:** interrupt each boundary, reorder replay, and prove convergence for the declared model.
3. **Trigger:** promoting or reverting a migration. **Failure:** request acceptance is mistaken for completion, or a retained table is mistaken for a viable rollback. **Mechanism:** observe all required components, validate transformed data, and check old-schema representability. **Limit:** tool strategy and retention matter. **Counterexample:** a new bigint value cannot fit the old int schema. **Verification:** reject premature promotion and unrepresentable rollback; retain a forward-repair alternative.

## Executed feasibility model

Ran `python3 /tmp/tal-skills-migration-feasibility.py` successfully during research. This temporary, standard-library-only script is not a repository implementation artifact. It models tuples, finite schedules, capabilities, and status flags; it performs no database operations. Six scenario groups produced:

| Model check | Observed result | Suggested durable fixture |
|---|---|---|
| Backfill versus live update | Enumerated 3 legal schedules. Unconditional copying fails for `snapshot → live_write → backfill`; a monotonic revision guard has zero failures in those 3 schedules. | One row starts at revision 1; a live write advances to revision 2; delayed revision 1 must not replace it. |
| Replay and revision identity | Identical replay leaves state unchanged; conflicting contents under the same revision are rejected. | Reuse a revision with different data and require an observable conflict. |
| Consumer compatibility | Old running jobs, queued jobs, and retained old rollback versions each independently block contraction; compatible remaining consumers permit it. | Pod inventory alone says ready while a durable queue entry still requires the legacy field. |
| Interrupted dual write | A crash between independent writes produces divergence. An assumed atomic source-plus-intent update followed by duplicate replay converges. | Make the atomicity assumption explicit and later test it against the selected real database. |
| Asynchronous cutover | Request acknowledgement and one completed shard keep the observation gate closed; completion of all required shards satisfies that gate. | Continue compatible operation between shard completions. This gate alone does not prove semantic data correctness. |
| Conditional rollback | Out-of-range values reject rollback despite an artifact; absent artifacts reject rollback despite representable values. | After widening int to bigint, write `2**31`, then reject an int rollback in the model. |

The model checks demonstrate counterexamples and acceptance predicates, not MySQL locks, SQL semantics, replication correctness, durable transactions, crash recovery, VDiff behavior, global atomic cutover, or production performance. Real integration evidence must use the chosen database/tool versions and test those boundaries separately. The finite three-schedule result is not an exhaustive proof over arbitrary concurrent programs.
