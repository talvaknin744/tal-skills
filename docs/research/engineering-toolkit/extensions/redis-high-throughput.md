# Redis under heavy read and write load

Research checked on 2026-09-29. The supplied discussion prompted this audit; it is not a source of verified claims. Its reviewed design ideas are adopted conditionally in [cache design](../../../../skills/engineering/microservice-operations/references/cache-design.md), within the existing skill. [The structured record](redis-high-throughput.json) contains source scopes, feature boundaries, seven practice cards, and proposed checks. None of those new checks ran in this pass.

The useful starting point is to identify Redis's role: disposable cache, authoritative state, or accepted work awaiting another store. A throughput optimization must preserve that role's acknowledgement, freshness, retention, and overload contracts.

| Advice under review | Correction and decision |
|---|---|
| Automatically replace synchronous database writes with Redis buffering | **Conditional.** An accepted enqueue is not a database commit. Choose an explicit loss window, persistence/failover policy, reconciliation path, and admission bound before acknowledging queued mutations. Batching does not make database capacity unlimited. [Persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/), [replication](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/) |
| A Stream or List supplies reliable write-behind | **Incomplete.** A destructive list pop can lose unprocessed work. A processing list or consumer group supports recovery, while database effects still need stable identity and atomic deduplication. Acknowledge after the effect commits. [LMOVE](https://redis.io/docs/latest/commands/lmove/), [XREADGROUP](https://redis.io/docs/latest/commands/xreadgroup/), [XCLAIM](https://redis.io/docs/latest/commands/xclaim/) |
| Stream length measures replication lag | **Incorrect.** `XLEN` counts retained entries. Group `pending` counts delivered, unacknowledged entries; group `lag` estimates undelivered entries and can be null. Server replication progress is a different history and offset. [XLEN](https://redis.io/docs/latest/commands/xlen/), [XINFO GROUPS](https://redis.io/docs/latest/commands/xinfo-groups/), [INFO](https://redis.io/docs/latest/commands/info/) |
| Primary reads or replication waits establish strong consistency | **Too broad.** Primary routing avoids ordinary replica delay while that primary remains authoritative. Async failover can still lose acknowledged history. `WAIT` checks replica receipt; `WAITAOF` checks AOF fsync counts. Both cover preceding writes on the same connection; inspect returned counts. Neither creates strong consistency or a database transaction. [WAIT](https://redis.io/docs/latest/commands/wait/), [WAITAOF](https://redis.io/docs/latest/commands/waitaof/) |
| `BCAST` cures invalidation storms | **Workload-dependent.** It removes per-key tracking state but broadcasts matching changes to every prefix subscriber, even those that never read the key. Narrow prefixes remove unrelated traffic; they do not eliminate hot-prefix fanout. Measure against ordinary/opt-in tracking or selective L1 bypass. [Tracking reference](https://redis.io/docs/latest/develop/reference/client-side-caching/), [command options](https://redis.io/docs/latest/commands/client-tracking/) |
| Duplicate a hot mutable key under random suffixes | **Requires a coherence design.** Copies only distribute load if routing reaches different resources; one standalone server remains one server. Cluster hash tags can colocate every copy. Partial updates, deletes, and delayed fills can diverge. Immutable version-addressed data is a narrower candidate; partitioned counters require defined aggregation semantics. [Cluster specification](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/) |
| Use volatile eviction and put TTL on every key | **Reject as a universal rule.** Volatile policies select TTL-bearing keys; TTL does not reserve a minimum retention period. Correctness metadata can disappear early. Choose loss eligibility explicitly and separate durable work/metadata from disposable cache data where appropriate. `noeviction` requires handling rejected writes. [Eviction](https://redis.io/docs/latest/develop/reference/eviction/) |
| All Redis work is single-threaded; always use UNLINK; cap every collection at a few thousand members | **Replace with measured command budgets.** Redis has I/O/background threads, while expensive ordinary commands can still delay others. Cost depends on command, bytes, response size, and workload. `UNLINK` detaches keys before background reclamation; it does not promise an immediate RSS drop. [Redis 8 I/O threading](https://redis.io/blog/redis-8-ga/), [latency](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/), [UNLINK](https://redis.io/docs/latest/commands/unlink/) |

Keep three failure boundaries explicit. First, a lost enqueue reply leaves acceptance uncertain; retry with the same operation identity. A timed-out persistence wait does not undo preceding writes: separate an unconfirmed durability target from a known or unknown write outcome. Second, a database commit followed by a lost acknowledgement permits redelivery. Third, reclaiming consumer ownership does not revoke an old worker's ability to affect an external database. These are application protocol requirements, inferred from the documented command boundaries.

Retention is part of recovery. Default `XTRIM` can remove an unacknowledged payload while leaving a pending reference. The `ACKED` policy is available from Redis 8.2 and considers existing groups' acknowledgements; it does not establish future replay needs or repair premature application acknowledgements. [XTRIM](https://redis.io/docs/latest/commands/xtrim/)

The highest-value follow-ups are bounded failure checks: commit then lose ACK; overload a stopped worker; disconnect an L1 invalidation channel; compare ordinary tracking with BCAST; interrupt one salted-copy update; and force metadata eviction before TTL. Replica freshness tests must distinguish offset progress from an application's required revision and exercise failover. All are proposals, not observed results.
