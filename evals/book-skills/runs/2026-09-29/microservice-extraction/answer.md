**Do not approve the current rollback plan.** After Address accepts writes, Address's current state is authoritative. Routing back to stale `main_db` and restoring its 01:00 snapshot would lose successful corrections and newly created addresses. It would also discard changes made in `main_db` between 01:00 and the 03:00 handoff. Support visibility is useful for diagnosis, but it is not a demonstrated recovery mechanism.

Two further blockers precede cutover: old workers can still write `main_db`, creating competing authorities, and stopping the stream at 03:00 does not prove that all committed source changes have reached `address_db`. A timed switch is insufficient. The handoff needs a source write fence, a final committed checkpoint, verified catch-up, and controlled routing.

The required invariant is clear: a successful correction must survive migration and recovery and be available when a customer places an order later that day. Identical fields and monotonic versions help compatibility, but do not establish reliable capture, delete handling, retry semantics, or a conflict-free handoff. The scope and enforcement of the versions are not described. A version must not be treated as proof that two independent writers cannot conflict.

Inventory request callers, old workers, direct database writers, delayed jobs, order-placement reads, caches, reports, and foreign keys before choosing the cutover set. Verify whether order creation needs the latest customer address or an intentional immutable order-address snapshot, and preserve that behavior. Unknown consumers and cross-database transaction dependencies are unresolved migration risks. The extraction's intended benefit and success measure are also missing; record them so retirement can be judged against a real result. A local address facade is a smaller initial change that may provide some maintainability benefit while leaving this extraction possible.

I would deploy the routing/compatibility seam first while `main_db` retains ownership, then copy and validate data, then transfer authority. This separates code deployment from the data transition. Moving data authority first would force every existing reader and writer to use the new owner immediately; given the surviving workers, that is currently riskier. Do not introduce application dual writes as a shortcut.

A global handoff of this bounded address capability is simpler than sending a random percentage of writes to each database. Canary new code while it still uses the same authority, and shadow reads before handoff. A write cohort would require a stable ownership partition and correct routing for every worker and order reader; the supplied plan establishes neither.

Recovery after Address accepts writes must follow current data authority:

1. Prefer keeping Address data authoritative while reverting compatible code or repairing the service. Do not serve corrections from the stale old copy. If continued mutation is unsafe, pause new address writes explicitly and preserve the acknowledged state; agree the acceptable pause budget before cutover. If current reads cannot be served, report unavailability rather than silently returning an older address.
2. If returning ownership to the monolith is necessary, stop Address writes, drain in-flight work, and establish a durable final Address checkpoint R. Fence Address against subsequent commits. Keep the old writer fence in place during reconciliation.
3. Apply every post-handoff mutation through R to the retained, validated `main_db` state from W. Capture must be durable with the authoritative commit, for example through verified database change capture or a transactional journal/outbox. It must include creates, updates, delete tombstones if applicable, stable identifiers, versions, and enough payload to recover the state. A support screen or best-effort request log is insufficient.
4. Make import resumable and idempotent. Preserve ordering/version semantics; safely ignore proven identical replays. Flag equal-version/different-payload or unexpected old-store changes for reconciliation rather than silently choosing a winner. Do not assume a highest-version rule resolves split-brain writes. Verify old code can interpret all imported fields and semantics; identical fields today do not guarantee compatibility after later changes.
5. Validate records, versions, existence/deletion, and all accepted corrections through R, including an end-to-end corrected-address order flow. Confirm no uncaptured committed mutation remains. Import checks must also cover interruption and retry. Only then route old readers to the reconciled store and reopen old writes, while Address stays fenced. Drain/reconfigure delayed jobs so none resurrects the former writer.
6. Retain the recovery journal, checkpoints, and Address data until the return is confirmed. If reconciliation cannot prove completeness, keep Address authoritative and repair forward or remain in the agreed pause. The current proposal has no safe immediate return path after new writes.

This procedure recovers data ownership. Reverting a binary or changing a route is a separate action. If address changes trigger downstream effects, inventory them and preserve effect identifiers/checkpoints so replay does not send duplicate notifications or repeat other actions. The brief does not establish whether any such effects exist.

The evidence gates need operational decisions before execution. No responsible person, error/latency targets, or acceptable pause duration is provided. Assign an accountable service owner and cutover decision owner; have the latter approve the observation windows and thresholds. The following are proposed gates, not measured results:

- **Before enabling Address writes:** zero unexplained state differences at W, all old writers fenced, all final source changes applied, and a passed recovery rehearsal showing zero loss of acknowledged corrections. Observe at least a complete representative writer/job cycle and simulate delayed worker recovery; the actual cycle duration must come from the inventory.
- **Before reopening monolith writes after recovery:** zero missing acknowledged mutations through R, no active Address writer, compatible imported state, successful restart/replay checks, and a passed later-order journey using the corrected address. Time pressure or a lower error rate is not a substitute for this gate.
- **During the recovery window:** any lost acknowledged correction, stale order-address read inconsistent with the contract, competing writer, or capture gap is a correctness stop condition. Use measured baseline and agreed targets for errors and latency; “error rate rises” needs a defined threshold and evaluation window. The first hour can be an intensive observation period, but cannot establish that later-that-day order reads and delayed workers are correct.
- **Before irreversible retirement or incompatible schema changes:** observe the later-order journey and the longest relevant scheduled/delayed work interval, prove no supported consumer uses the old path, verify restore/recovery evidence, and explicitly close the old-code recovery window. Keep changes additive during coexistence. Do not delete the only copy or journal containing an accepted change.
