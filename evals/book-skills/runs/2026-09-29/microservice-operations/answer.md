The configured retries can amplify 200 client requests/second into **1,800 Inventory attempts/second**, a ninefold load increase. The bounded correction is to remove timeout retries at both layers for this outage, enforce one propagated request deadline, and cap Inventory-related concurrency with immediate overload rejection. These are proposed changes; [incident.md](/tmp/book-skill-trials-20260929/microservice-operations/project/incident.md) is the only supplied operational evidence.

With every attempt timing out and all configured retries reached:

| Boundary | Attempts per original client request | Offered rate at 200 client requests/second |
| --- | ---: | ---: |
| Client → Gateway | 1 | 200/second |
| Gateway → Checkout | 3 | 600/second |
| Checkout → Inventory | 3 × 3 = 9 | 1,800/second |

Relative to one Inventory check per client request, retries add 1,600 attempts/second: an 800% increase, with total load at 900% of the no-retry baseline. These are configuration-derived rates after retry activity reaches steady state, assuming resources allow all attempts to start. Queuing or admission limits can change actual throughput. Client retries are explicitly outside the 200 requests/second and can increase these totals further; there are no additional retry layers below Checkout in this estimate.

Each Checkout invocation can spend about three seconds waiting on three sequential one-second Inventory timeouts, before overhead. If Gateway waits for each entire Checkout invocation, three such invocations can take about nine seconds. Gateway's per-attempt timeout is not provided, so nine seconds is not an established observed latency or a hard upper bound. Earlier Gateway timeouts can overlap Checkout work because callers do not cancel it; queues and scheduling can lengthen completion. There is no overall deadline enforcing the desired two-second response.

The main propagation risks are:

- Immediate retries multiply offered load precisely when Inventory is slow, delaying recovery and potentially aligning retry bursts. Read-only calls avoid duplicate-write concerns but still consume resources.
- Missing propagated deadlines and cancellation allow Checkout and Inventory work to outlive the requesting client, consuming capacity without a useful response.
- Slow Inventory waits can exhaust Checkout/Gateway workers or connection pools, grow queues, and affect unrelated traffic if resources are shared. Their pool topology and limits are not supplied, so this is a risk to verify, not an observed measurement.
- Timeout completion does not prove remote work stopped. With 1,800 attempts/second each waiting one second, roughly 1,800 outbound Inventory waits would be concurrent in an unconstrained steady state. This is a calculated occupancy estimate, not a measured server concurrency limit; uncancelled server work can persist longer.

Apply the following small operational change together:

1. Set Gateway to one Checkout attempt and Checkout to one Inventory attempt for timeouts. For the stated traffic, Inventory offered load is then at most 200 attempts/second before any admission rejection. Do not merely move all nine attempts into one layer. If retries are later justified by transient-failure evidence, permit them at one designated layer only, with jitter, a retry budget, and sufficient remaining deadline; leave them disabled during this correction.
2. Set a proposed two-second Gateway deadline, measured from acceptance of a request to completion of its response. Reserve 200 ms for mapping errors and returning the response, leaving at most 1.8 seconds for downstream work. Propagate remaining time through Checkout; include pool acquisition, queueing, connection establishment, and response waiting. Keep each Inventory attempt at no more than one second and shorten it further when the remaining parent budget requires that. Return a clear temporary-unavailability response, such as HTTP 503, rather than interpreting a failed availability check as either available stock or an authoritative out-of-stock result. Verify existing clients handle that response.
3. Cancel outstanding downstream work when the deadline expires or the caller disconnects, and release local resources. Verify server-side deadline/cancellation behavior separately: if the transport only abandons the response, enforce Inventory-side expiry/admission too before claiming remote work is bounded.
4. Isolate Inventory calls behind a concurrency cap `C` with no waiting backlog: reject excess work promptly. Select and record `C` from an authorized healthy-load capacity check and actual worker/connection limits, leaving resources for unrelated work. Neither those capacities nor a safe numeric cap is in the snapshot. This missing value is a pre-rollout gate, not a reason to choose an arbitrary pool size. Keep the normal traffic and retry configuration bounded after recovery; with no queued backlog there is no catch-up surge to drain.

Deadlines and admission limits provide the initial containment. A circuit breaker is not required to complete this correction; adding one later would require its own opening rule, fail-fast behavior, bounded recovery probes, and close criterion.
