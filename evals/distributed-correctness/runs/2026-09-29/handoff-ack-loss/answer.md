The progress-read/three-ACK-retry patch does not establish safe recovery. It still permits both failures shown in the supplied traces. The minimal repair is a terminal-state replay check plus database-enforced ownership and checkpoint guards on every business transaction. The database can atomically protect rows, progress, and completion under the supplied contracts; a distributed transaction with the queue is unnecessary.

This is a read-only review using the supplied graceful-draining skill. Evidence comes only from `project/observations.md` and `project/worker.pseudo`; the protocol and schedules below are proposed, not executed or verified against a live queue or database.

**Findings from the supplied evidence**

1. **Completed exports are finalized again.** In trace 1, ex-27 has durable rows through offset 999 and a committed summary plus `completed` state before the ACK timeout. B acquires ownership generation 18 and appends another summary even though the state is still completed (`observations.md:20–25`). Reading only `next_offset=1000` skips the loop but falls through to the unconditional finalization transaction (`worker.pseudo:5–15`). Three ACK retries merely reduce the chance of a redelivery; they cannot make it impossible. An ACK timeout alone cannot distinguish an accepted ACK whose response was lost from a request that never arrived (`observations.md:3–6`). Neither outcome justifies repeating export effects, reverting completion, or declaring a business failure.

2. **The old owner can corrupt both output and progress.** In trace 2, A computed offsets 40–49 at generation 4, then its lease expired. B acquired generation 5 and durably advanced `next_offset` to 70. A resumed and appended duplicate rows and moved progress backward to 50 (`observations.md:31–34`). A progress read, even immediately before processing, becomes stale during suspension. Atomic row/progress writes do not help if an unauthorized owner can commit the whole transaction. Unconditional methods retain exactly that vulnerability (`worker.pseudo:8–10`; `observations.md:10–15`). New physical row IDs do not identify the same logical input offset.

3. **Heartbeat logging is not fencing.** Suspension preserves the handler and its database access. Renewal rejection only logs (`worker.pseudo:17–19`). Local cancellation is useful but cannot stop a paused handler from later reaching a write. Summary, terminal-state, renewal, and any release/cleanup operations need protection as well as chunk writes; otherwise late finalization or cleanup can corrupt a successor's work.

The traces show data-integrity failures, not evidence of a broker retry-budget failure or an application business failure. Ownership generations 4/5/18 are lease epochs; no deployment-generation policy, queue implementation, framework ACK behavior, delivery-attempt limit, or logical-job deadline is supplied. Database ownership leases and queue delivery leases must be treated separately.

**Minimal coherent recovery protocol**

Use the existing `exports` row as the durable authority for a stable `export_id`. Define `next_offset=c` to mean that exactly the intended output for offsets `[0,c)` is committed. `COMPLETED` is an absorbing state and means all manifest offsets and exactly one summary committed. Retain this record for every permitted replay/redrive; if replay has no bounded horizon, deleting the terminal record would remove the replay protection.

1. **Resolve terminal state before acquiring work.** Read from the authoritative database. If `COMPLETED`, perform no transform, row append, summary append, or state reset; ACK this delivery. Otherwise atomically claim only an eligible nonterminal export with an expired lease, incrementing its generation. Claim must serialize with completion, recheck state, and return the authoritative cursor and ownership tuple. If another owner is active, leave the delivery unacknowledged or use the queue's supported deferred/retry disposition. A plain handler return must not implicitly ACK unfinished work. An ACK is permitted later if durable completion has actually been observed.

2. **Commit each bounded chunk under a transaction guard.** Capture `(export_id, owner, generation, expected_offset=c)`, compute the immutable manifest slice `[c,e)`, where `e=min(c+10, manifest.length)`, then lock/conditionally update the export row in the same SQL transaction as output writes. Require a nonterminal state, the current expected owner and generation, a still-valid lease according to authoritative database time, and `next_offset=c`. Insert rows and set `next_offset=e` only if all guards hold. A failed guard aborts the entire transaction, including inserts. The checks must serialize against competing claims, renewals, finalization, and chunk commits; a snapshot read followed by unconditional writes is insufficient. Use the supplied storage API's transactional fencing rather than its default unconditional calls.

   The expected-offset guard is necessary for replay of an uncertain commit and for concurrent handlers accidentally using the same ownership token. Both could otherwise pass an owner/generation check and append the same chunk twice. If a commit response is lost, read durable state again. If the cursor advanced, do not reinsert that chunk; if it did not, retry only through the full guard. On ownership loss, discard local work and stop. Never write the local cursor back just because it was previously read.

3. **Finalize once, within the same guarded database boundary.** Require current owner/generation, a valid lease, nonterminal state, and `next_offset=manifest.length`. In one transaction append the summary and change the state to `COMPLETED`. A competing or repeated finalization must observe completion and append nothing. This covers a crash or lost response after the summary transaction commits. The last partial chunk must advance to the actual manifest length; the current unconditional `cursor+10` can overshoot it.

   Serializing every writer through this state/cursor guard makes the existing physical append scheme sufficient for future logical uniqueness, starting from consistent data. Unique keys on `(export_id, input_offset)` and a single summary key per export are useful additional enforcement if the schema supports them, but they do not replace fencing or atomic progress updates. The proof fails if any write path bypasses the transaction guard. An outbox, external-effect ledger, or provider deduplication service is not needed for the supplied single-database effects.

4. **ACK only after durable completion, and separate ACK outcome from export outcome.** Retry an ACK only according to the queue API's rules for that delivery receipt. Three failed/ambiguous responses leave delivery settlement uncertain, while the export remains durably completed. If the ACK succeeded, no further business work is needed. If it did not, any later delivery follows the completed-state path and attempts its own ACK without effects. Do not depend on learning whether the original ACK succeeded, or on ACK retries eventually succeeding within this handler. Keep terminal records and log settlement trouble separately from business failures.

5. **Make lease loss and interruption recoverable.** Renew only the current nonterminal owner/epoch under a valid lease; an expired token must reacquire through a fresh claim, not revive itself. Fence release/cleanup so A cannot clear B's ownership. Stop new work on renewal rejection as an optimization; database guards provide the actual protection. During planned interruption, finish or abort a bounded chunk and retain unacknowledged delivery until completion. After an aborted transaction, a successor resumes at the last committed cursor. After a committed transaction with an unknown client response, it reads that committed cursor. No incomplete export may lose its only trigger through an ACK.

   The supplied queue contract provides redelivery after its delivery lease expires when no ACK arrived. Continued progress additionally requires an available compatible worker and database. The queue's behavior when a delivery handler returns, independent retry/DLQ limits, receipt reuse rules, and actual transaction isolation still require implementation evidence. Establish finite logical-job age/progress-stall policies and visible escalation for unfinished exports; three ACK retries are not a job deadline. If an actual broker can exhaust deliveries, use its durable DLQ/reconciliation path to retain discovery of unfinished export IDs. Do not assume that an application counter overrides broker policy.

**Recovery of the already affected exports**

The protocol prevents new corruption; it does not repair existing duplicates. Ex-27 already has a duplicate summary, and ex-28's saved cursor of 50 no longer reliably describes its committed outputs. Before replay, exclude the old unconditional writer paths, fence current ownership, and reconcile actual rows and summaries against the immutable manifest. Restore one logical row per offset, one valid final summary when complete, and a cursor describing the reconciled contiguous output. The supplied files do not show whether stored rows retain an input-offset identity; if that mapping cannot be recovered, a controlled reconstruction into a validated replacement output may be needed. Do not blindly resume ex-28 at 50 or assume the largest previously observed cursor proves clean data. No repair or redrive was performed in this review.

**Failure schedules to verify — proposed checks, not test results**

| Schedule | Required observation |
| --- | --- |
| Finalization commits; ACK request never reaches the coordinator; all three retries fail; delivery lease expires. | B reads `COMPLETED`, adds zero rows and zero summaries, and ACKs its delivery. Exactly one summary remains. |
| Finalization commits; coordinator accepts ACK but its response is lost. | Export remains completed regardless of client retry outcome. Any permitted duplicate delivery also produces no effects. |
| Pause A after computing 40–49 at epoch 4; let its lease expire; B at epoch 5 advances to 70; resume A. | A's entire transaction is rejected. No extra 40–49 rows and no cursor regression; cursor remains at least 70. |
| Pause A after a preliminary ownership check but before its write; transfer ownership. Also let A's lease expire without a successor. | The transaction-time guard rejects A in both cases; neither a pre-check nor absence of a new owner authorizes an expired token. |
| Two handlers use the same epoch and expected cursor, or a chunk commits but its response is lost and the client retries. | Only one transaction can advance that cursor and append its chunk. Recovery reads committed progress. |
| Crash after row insertion but before progress update/commit; then repeat with a crash just after commit. | Before commit, both rows and progress roll back. After commit, both survive and replay skips the chunk. |
| Crash after summary insertion but before commit; then lose the response after finalization commit. Race finalization with a new claim. | Summary and terminal state appear together or neither appears. Exactly one finalization wins; completed state is never reopened. |
| Resume stale A's renewal, release, cleanup, and finalization after B acquires ownership. | Every stale mutation is rejected; B's ownership and progress remain intact. |
| Repeatedly interrupt A, then B, then C at different chunk boundaries. | Same export identity, increasing ownership epochs, monotonically advancing committed cursor, no duplicate logical offsets, and eventual completion or explicit stall/deadline escalation. |
| Persisting progress fails until a drain deadline, or delivery arrives while another owner is active. | No premature ACK, no partial committed effect, unfinished work remains discoverable, and recovery resumes the last durable cursor. |
| Empty manifest and a final slice shorter than ten rows. | Cursor equals the exact manifest length; one summary, no skipped or invented offsets. |
