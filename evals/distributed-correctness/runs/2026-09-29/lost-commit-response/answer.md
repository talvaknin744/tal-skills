The required contract is one durable outcome per immutable request ID: identical deliveries return the same result, different intent under that ID is rejected, and a successful obligation applies exactly one debit. A pending/unknown response must not assert either success or failure. No additional overdraft rule is specified here.

Use the existing database transaction and `outcomes.request_id` uniqueness constraint as the enforcement boundary. Every delivery and recovery path must use this protocol:

1. Preserve the original `request_id`, account, and amount. Compare all intent-bearing fields using a defined canonical representation; never substitute a new request ID for a retry.
2. In a fresh transaction, generate a candidate debit ID and prepare the complete result, for example `{status: "accepted", debit_id: candidate}`. **Insert the outcome first**, with the request ID, accepted payload, and result. Its `result NOT NULL` requirement is satisfied by this prepared result. The row remains uncommitted during the following work.
3. Only after successfully inserting that row, insert the debit and decrement the account in the same transaction. Check that the intended account was actually updated; any unsuccessful operation must abort the whole transaction. Commit the outcome, debit, and balance change together. No committed outcome may precede its debit, and no debit may commit without its outcome.
4. Return the stored result after acknowledged commit. If the request ID already exists, do not mutate the account. End/roll back the competing transaction as required by the driver, then use a fresh leader read to retrieve the committed outcome. Return its exact result if the payload matches; otherwise reject ID reuse. Do not overwrite the original payload or result.

This ordering is essential: an initial “does the outcome exist?” read alone cannot exclude concurrent duplicates. The unique insert arbitrates ownership, including against an original transaction still finishing. The database commit is the durable success point. After the original commits, a competing claim loses and replays that outcome; after a confirmed original abort, a contender can acquire the key and perform the debit. Fresh reads avoid relying on a failed transaction or an old snapshot. Only the supplied database capabilities are assumed; deployed driver error and transaction-state handling still need verification.

Handle recovery according to evidence:

| Observation | Recovery |
| --- | --- |
| `SerializationFailure`, explicitly documented here as a confirmed abort | Retry the entire transaction, including its decision reads, with the same request ID and intent and fresh transaction state. |
| Lost connection or timeout at COMMIT | Mark the outcome unknown. Reconnect within the remaining budget and query the leader by request ID. A matching durable row establishes success; a different payload establishes ID conflict. |
| Leader lookup returns no outcome | This does **not** prove the original aborted: it may still be uncommitted. Retry only through the outcome-first transaction above. Its unique insert waits for/arbitrates with the original; never directly replay the debit. |
| Authority unavailable, unresolved claim, or deadline expires | Return `{status: "pending", request_id: original_id}`. Later status lookup or redelivery must preserve that ID and use the same protocol. Do not instruct the caller to create a new obligation. |
| Other errors | Classify explicitly. A validation error or persistent database error is not a generic transient retry. Return a definite failure only when non-commit is established and no earlier attempt remains unresolved. Persist terminal business decisions if they are part of the repeated-delivery outcome contract. |
