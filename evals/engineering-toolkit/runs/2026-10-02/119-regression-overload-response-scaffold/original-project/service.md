# Shared report service
Four pods each admit up to 40 simultaneous HTTP requests with a FIFO waiting queue of unlimited size. Each admitted report invokes three database queries concurrently, using separate connections. The shared database allocates at most 100 connections to this service. All tenant identifiers come from verified authentication context.
Tenant A offers 1000 reports/s; tenant B offers 10 reports/s. Requests vary from 5 ms metadata lookups to 500 ms large exports. B's metadata lookups have a 100 ms objective. A token bucket meters equal request counts for both classes. The proposed per-pod concurrency cap is described as a global database cap and as proof that B cannot starve.
The service also accepts durable asynchronous exports: HTTP 202 is sent after job persistence, and those jobs must eventually complete with their documented effects. A caller disconnect does not stop an already issued query. The draft releases admission permits immediately on disconnect and deletes old queued exports when overloaded.
Every caller retries 503 immediately three times. The adaptive controller uses a histogram mixing 1 ms rejection responses with successful work and raises its limit when that histogram's median falls. Autoscaling uses completed request latency alone. No overload recovery test has run.
