**The rollout does not satisfy either requirement.** The [contract](../final-project/adapter-contract.md) sets a 500 ms useful response target from admission, including acquisition, and requires exclusive connection ownership through send cleanup.

- **Deadline:** [handler.py](../final-project/handler.py) passes a wall-clock epoch to `asyncio.timeout_at()`, which uses the event loop’s clock. Acquisition is outside that timeout, and the separate 500 ms wait starts afterward. In the supplied [synthetic trace](../final-project/trace.jsonl), admission is at loop time 400.0 and the response is at 400.602: **602 ms**, or 102 ms past target.
- **Connection lifecycle:** On a pending send, `child.cancel()` requests cancellation but does not wait for cleanup. The `finally` block releases the connection immediately. The trace shows release at 400.601, reuse at 400.61, and child cleanup only at 400.95. Upstream cancellation during the wait has the same risk because `asyncio.wait()` does not cancel its child.

**Bounded correction:** Set one deadline at admission using `loop.time() + 0.5`, capped by any earlier upstream deadline. Apply its remaining budget to acquisition and response waiting, and propagate upstream cancellation. Establish connection ownership immediately after acquisition. If a send is still active when the caller’s budget expires, transfer the task and connection to supervised cleanup: request cancellation, keep the connection unavailable, and release it only after the task actually finishes. Return an explicit *outcome unknown* state for a dispatched shipment; look up its receipt using the stable `shipment_id` before any resend. Cap retained connections and apply backpressure when that cap is reached.

This bounds resource use, but the supplied contract gives no maximum send cleanup time or forced-stop guarantee, so **connection recovery time cannot yet be guaranteed**. Acquisition cancellation behavior and release behavior also need verification before claiming a firm 500 ms response bound.

For rollout checks, observe: expiry during acquisition with no leaked connection; an earlier upstream deadline and cancellation during send; cancellation after carrier acceptance with no premature reuse and receipt reconciliation; and a subsequent useful send completing after cleanup. Record admission-to-response latency, task completion, connection ownership/reuse, retained-connection count, backpressure, and receipt outcome.
