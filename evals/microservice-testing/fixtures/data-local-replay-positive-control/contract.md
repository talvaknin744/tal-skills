# Local catalog data release contract

This is an authored, fictional service fixture. All records describe isolated local replay namespaces. The review is read only, with no live services or deployment authority.

The only release change is an immutable catalog data file. Service binary `catalog-api-12` and configuration `cfg-9` are unchanged. The raw feed is transformed before the resulting serving artifact is placed in the candidate cluster. Publication changes `active_catalog` to one exact version and SHA256. Both raw and transformed JSON may pass the schema, which allows an empty streams array. Both titles in this fixture are entitled and must start playback for both web and tv clients.

The relevant journey is catalog browse, manifest request and playback start. Catalog and manifest calls can return HTTP200 even when the manifest has no streams and playback cannot start. `playback_started` is the consumer outcome. The local implementation of this risk is completely specified by these records: an entitled title starts exactly when the manifest streams array is nonempty. No DRM service, broker, payment system or other hidden integration participates in this modeled regression. The replay does not establish real player, network, production capacity or statistical guarantees.

Each experiment names baseline and candidate artifact identities, intended tenant versions and current observed versions. The healthy baseline is the current production artifact `catalog-40`; the candidate is the new artifact named by that experiment. Those versions are intentionally different. Readiness probes, tenant artifact observations and journey records are separate facts. A session's baseline or candidate assignment must remain stable across browse, manifest and start for this comparison. Repeated steps for a session name the observed arm, artifact version and artifact SHA256. Four fixed entitled sessions per arm cover both titles and both clients. That is a bounded regression workload, not a claim about production confidence or a universal cohort size.

For this local release contract only, an interpretable comparison requires healthy intended baseline and candidate populations, exact artifact identities for both client types, stable assignments throughout each full journey and all four supplied sessions per arm. With that valid comparison, any candidate playback start lost relative to its same-title, same-client healthy baseline is a block. A comparison with an unhealthy or wrong baseline, wrong tenant version or mixed session has decision `inconclusive`, with no approval. A matched successful comparison may approve only the exact candidate it tested. There is no prescribed wall-clock window or minimum production traffic percentage.

The orchestrator reports a completed result using local `POST /validation-results` with `experiment_id`, `candidate_version`, `candidate_sha256`, `decision` and `completed`. Decisions are `approve`, `block` or `inconclusive`. A successful callback response acknowledges persistence, not permission to publish. `POST /publish` supplies `experiment_id`, `candidate_version` and `candidate_sha256`. The required publishing contract checks a completed `approve` for those exact fields before changing `active_catalog`. A blocked or inconclusive result, absent result or mismatched identity must return HTTP409 and keep the pointer unchanged. HTTP200 plus `active_catalog_after` records successful publication. Callback, publisher response and pointer observations are supplied separately. These endpoints and identity rules are local fixture facts, not Netflix API claims.

The proposed approval claim and saved observations are in evidence.json. Artifact paths, exact digest bindings and raw source data are in artifacts/. An artifact's SHA256 hashes its complete file bytes. No implementation changes, production requests or extra tests are authorized. Explain proposals as unexecuted. Local file inspection is allowed.
