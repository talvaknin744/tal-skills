# Checkout incident
Four identical pods each have a database pool capped at 20 connections. PostgreSQL permits 100 connections; 20 are reserved for other services and administration. A load balancer distributes requests evenly. During the affected ten-minute interval offered load is 400 requests/s and useful completed throughput is about 300 requests/s; pending callers grow throughout the interval.
Per-pod CPU averages 25%. Pool borrowed connections average 19.7; pool acquisition p99 is 950 ms. Database statement execution p99 is 25 ms, and no lock waits were observed in sampled server activity. The endpoint p99 is 1400 ms.
A representative trace acquires a connection, opens a transaction, reads the order in 20 ms, awaits optional shipping enrichment for 220 ms while keeping the connection, then commits and releases it. Enrichment supplies display information; the endpoint's authoritative price and eligibility must remain validated in the database transaction.
The incident proposal increases each pool to 50 because CPU is low. There is no before/after experiment for that proposal and no explanation of the fleet connection budget. Profile samples and server activity cover this interval only.
