The relevant path is admission → connection acquisition → transaction/order read → shipping enrichment while retaining the connection → commit/release → response. Each pool averages 19.7 of 20 borrowed connections, or 98.5% occupancy, and acquisition p99 is 950 ms. The representative trace holds a connection for at least approximately 240 ms: a 20 ms order read plus a 220 ms network await, before commit overhead. Short statement execution p99 (25 ms) and no lock waits in sampled activity favor connection ownership over slow SQL as the immediate explanation. They do not rule out database or runtime constraints outside the sampled window. CPU averaging 25% does not establish spare connection capacity or exclude CPU bursts, scheduling delay, or effective container limits.

The trace also makes the saturation plausible quantitatively: if its roughly 240 ms ownership were representative of the mean, 400 requests/s would require approximately 96 concurrently borrowed connections, exceeding the fleet's 80. This is an illustration, not a measured mean or a capacity forecast. Pool-acquisition and endpoint percentiles describe separate distributions; they cannot be added or subtracted to reconstruct a p99 critical path. Correlated slow-request traces are needed for that attribution.

Do not adopt the proposed pool increase. Four pools of 50 request up to 200 connections; PostgreSQL allows only 80 for this application after its 20 reserved connections. The current four pools already exhaust that budget. More borrowers would shift waiting or failures downstream and cannot be justified by low average CPU.

The one bounded intervention is to move only the optional display enrichment after commit and connection release, while continuing to await it before delivering the existing response. Keep authoritative price and eligibility validation within the same enforcing database transaction. Pass the needed order data out of the transaction without retaining its connection. Keep pool sizes, retry policy, enrichment calls, deadlines, response fields, and existing fallback/error behavior unchanged. This removes approximately 220 ms of connection ownership on the supplied trace; it does not remove that dependency from response latency. It should reduce pool occupancy and acquisition waits if this trace represents the affected cohort.

Inspect the actual transaction and endpoint code before implementation: the incident provides no code proving rollback, cancellation, snapshot, or ordering contracts. If enrichment failure currently determines an authoritative mutation's commit, or enrichment supplies inputs to price/eligibility validation, moving it after commit would change behavior; stop and resolve that contract before making this change. No implementation or experiment was performed in this review.
