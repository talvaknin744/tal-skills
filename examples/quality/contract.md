# Credit adjustment contract

This is a sequential, in-memory model with one ledger per trial and no external
effects. Its purpose is cleanup and testing evidence, not a production payment
implementation.

`credit(key, policy, amount, fault="none")` issues one named credit. Keys must be
nonempty strings. Policies are `support` and `goodwill`; each independently permits
exact built-in Python `int` amounts 1 through 100 inclusive. Booleans, floats, and strings are invalid
amounts. The equal limits have separate owners and reasons to change.

Validation occurs before replay lookup: key, then policy/amount, then fault.
An invalid retry is rejected as invalid input even if its key already exists.
Errors have the exact messages recorded in the golden cases. Fault values are
`none`, `before_commit`, and `after_commit`; other values are invalid.

A key binds the full `(policy, amount)` payload. Matching replays return the
original receipt without another effect. Reusing the key for a different valid
payload raises `RequestConflict`. Receipts count committed credits in order as
`credit-1`, `credit-2`, and so on; rejected inputs do not consume a receipt.

On a new valid command, `before_commit` raises `TransportFailure("before commit")`
without reserving a key or changing state. `after_commit` commits the effect and
receipt, then raises `TransportFailure("response lost after commit")`. An existing
matching replay returns its receipt regardless of the selected valid fault because
it performs no new commit. A lost response therefore reports an unknown outcome to
the caller; inspecting/replaying the model reveals the already committed credit.

`snapshot()` exposes the balance, ordered journal, and key-to-payload/receipt map.
Balance and amounts preserve their integer JSON representation; object-key order
is immaterial, while journal order is contractual.
Journal append and receipt recording form one uninterruptible sequential model
step. There is no claim about a real database transaction, concurrent requests,
process restart durability, provider effects, or cancellation.

Golden histories are hand-authored requirements, not generated by either
implementation. They include return/error observations and final ledger state.
The fault-schedule check also asserts a fixed single-credit state against 27
three-attempt schedules followed by a successful retry. These expectations do not
reuse either implementation's calculation or a second copy of its state machine.
