## Six-dimensional findings

### F1: permission to maintain precedes permission to read

- **Trigger:** Servers concurrently interpret shared data using different schema versions.
- **Problem:** A reader can use a new index while an older writer omits its maintenance, producing incorrect answers.
- **Mechanism:** Preserve both adjacent versions’ invariants; adding an index passes through delete-only and write-only permissions before readers may use it. Permit only one version of lag, advance at most once per lease period, and reject expired-schema writes at storage commit. Begin backfill only after delete-only writers lose commit eligibility and every eligible writer maintains the index; expose reads after reorganization.
- **Limits:** The proof assumes F1’s shared transactional storage, schema interpretation and lease/commit machinery. Application deployment versions do not automatically inherit it. Lock-coverage changes need their own timestamp-preservation protocol.
- **Counterexample:** Waiting for a server’s refresh timer does not prevent its paused, expired-schema write from committing later.
- **Verification:** Proposed: pause a writer across the version boundary, mutate and delete indexed rows during reorganization, and compare index answers with a base-data oracle. Verify rejection at the protected commit, not only a refresh log.

This card paraphrases the [full paper](https://research.google.com/pubs/archive/41376.pdf); proposed schedules and oracle requirements are independent synthesis.

### gh-ost: controllability and cutover are separate contracts

- **Trigger:** A live MySQL table needs a structural change while serving writes.
- **Problem:** Migration work competes with serving traffic, and an apparently finished copy may omit subsequent mutations.
- **Mechanism:** Tail row-based binary logs into an altered shadow table; serialize copying and event application. Throttle migration writes and postpone cutover while continuing catch-up when appropriate. Replica test mode freezes replication for original/shadow comparison.
- **Limits:** Historical motivation is not a current MySQL capability matrix. Replica tests do not reproduce all primary contention or application-version behavior.
- **Counterexample:** Successful row copying does not prove the shadow is caught up, or that old application SQL accepts the new schema.
- **Verification:** Proposed: include concurrent update/delete, pause/resume, binlog backlog and a long transaction obstructing cutover. Compare transformed rows at a common source boundary, plus foreground outcomes and acknowledged writes.

The [2016 account](https://github.blog/news-insights/company-news/gh-ost-github-s-online-migration-tool-for-mysql/) supplies the mechanism and its reported testing practice. No GitHub production results are claimed as our validation.

### Shopify: schema publication is a fleet-wide application boundary

- **Trigger:** A Rails application uses cached schema metadata while shards complete migrations independently.
- **Problem:** An arbitrary shard can supply a schema that other shards do not yet serve. Reverse replication can also encounter a uniqueness violation when events from different shards arrive in a different order.
- **Mechanism:** Keep changing columns out of generated application SQL during transition; publish a schema-cache dump only after every shard completes and no competing migration remains. Verify future routing/transaction constraints before sharding.
- **Limits:** `ignored_columns` affects Active Record’s model SQL, not every handwritten SQL path or external writer. The account’s reverse-replication error concerns a specific resharding flow, not every schema migration.
- **Counterexample:** Merely retaining the old database does not establish a usable rollback target after new writes diverge or reverse replication stops.
- **Verification:** Proposed: vary shard completion order, restart a process with a cached schema, and exercise direct SQL. For a reversible traffic switch, inspect reverse-stream progress and reconcile post-switch acknowledged mutations before declaring recovery available.

These details come from the [2024 account](https://shopify.engineering/horizontally-scaling-the-rails-backend-of-shop-app-with-vitess). Its performance figures and success statements are not our measurements.

## Concrete overlapping-version sequence

The following is an **original proposed rehearsal**, not Stripe’s undisclosed concurrency protocol, an F1 implementation, or a tested universal migration recipe. It changes `orders.status_text` to a coded representation: `pending → 0`, `paid → 1`. Every original V0 writer already increments a per-row `source_rev` transactionally on business changes; every row creation has an immutable, non-reused `source_incarnation`. If those prerequisites are absent, choose another enforceable concurrency protocol before using this schedule.

1. **Expand without exposing.** Add nullable `status_code` and `mapped_rev` using the selected engine’s supported algorithm. Keep both columns out of application-generated SQL during partial shard completion. Observe actual schema on every required shard before a bridge begins writing them; do not publish a cache from whichever shard answers first.
2. **Introduce V1 bridge writers.** In one local transaction, write the old text, new code, next `source_rev`, and matching `mapped_rev`. V0 may still write only text and increment `source_rev`; a mapped value can therefore become stale even when non-null.
3. **Run a bounded backfill.** Read text, incarnation and revision in one consistent row snapshot; compute the code, and conditionally update the still-existing row only when both `source_incarnation` and `source_rev` match that observation. Set `mapped_rev` to that revision. On mismatch, reread/reconcile. Do not insert a row that disappeared. Track required source membership, coverage and catch-up; a cursor’s end alone is insufficient.
4. **Allow V2 readers with a compatibility rule.** Read text, code and both revisions in one consistent row snapshot. Use a supported, non-null code only when non-null `mapped_rev == source_rev`; otherwise derive the answer from authoritative text. Keep predicates on a path that includes stale/unmapped rows. An index on code alone cannot find rows whose text changed under V0 but whose code did not.
5. **Close the V0 writer boundary.** Stop new admission and account for queued jobs, retry/replay entry points and open transactions. Enforce the chosen version floor at the actual write/commit boundary or prove those writers drained. A deployment percentage and an expired process heartbeat do not prove this. Complete the final reconciliation and the engine’s index publication checks before code-only predicates become authoritative.
6. **Keep a rollback-compatible interval.** V2 reads the new representation; V1 still maintains both. Preserve the old readers’ supported values and old schema while their rollback/replay contract remains active. Keep rollback writers behind the V1 bridge. If rollback must reactivate V0-only writers, first restore V2’s text fallback and stop code-only predicates; otherwise retain the writer floor. Rehearse old code against post-switch writes.
7. **Retire deliberately.** Only after old readers/writers and recovery dependencies are accounted for may V3 stop maintaining the old text and remove it. Record that accepting a new value such as `archived → 2`, which V0 cannot interpret, or destroying the old representation changes the recovery options.

The revision pair and conditional update are assumptions of this example, not capabilities supplied by online DDL. Cross-database dual writes need durable partial-success tracking and reconciliation; the example’s local transaction does not establish atomicity across separate stores.

## Independent oracle and adverse schedules

Use an independently maintained fixture ledger of **definitively committed business operations**, transaction identities, authoritative incarnations/revisions, rejected attempts, and manually specified expected statuses/deletions. Record acknowledged operations and reconcile unknown outcomes before comparison; response arrival order is not commit order. The oracle must not call the migration’s transformation code or infer correctness from a job-success flag. Freeze rehearsal writers after a reconciled commit boundary H, or use an engine-supported common snapshot/log boundary. Enumerate both expected and actual base/index identities and values at H; require exact set equality in both directions, including missing rows, extra/resurrected rows and orphan index entries, then compare query answers. Production need not adopt the fixture’s pause; its actual snapshot/catch-up contract needs separate proof.

| Deliberate schedule | Required observable result |
| --- | --- |
| Backfill reads pending/revision 1; V0 commits paid/revision 2; old backfill resumes | Old conditional update affects zero rows. V2 returns paid through the compatibility path; later reconciliation maps revision 2. |
| Backfill reads row B; V0 deletes B; backfill resumes | No resurrection; B is absent from all authoritative answers at H. |
| Backfill reads B/incarnation X/revision 1; delete and recreate B/incarnation Y/revision 1; old backfill resumes | Incarnation comparison rejects the old result. New B’s acknowledged value survives; equal revisions alone cannot authorize an update. |
| V1 commits a new status/revision; an older copy is replayed | Acknowledged new value survives; the oracle matches both representations when their revisions match. |
| One shard completes before another; a new process refreshes its cache | New-column exposure remains gated; ordinary requests do not depend on a schema absent on another required shard. |
| V0 pauses before commit, then resumes after the version floor | The protected boundary rejects the unsupported write, or verified draining establishes that no such transaction remains. No success acknowledgement is invented. |
| Concurrent unique-index build fails, or table-swap attempt times out | Inspect engine state and query/write behavior. Failed build status alone does not prove constraints are absent; failed cutover does not imply writes stopped. |

For an F1-style engine-index protocol, also pause a delete-only writer across the backfill entry gate. Backfill cannot begin while that writer may still commit without inserting index entries. After the gate, its expired-schema commit must fail. This engine-specific condition is separate from step 3’s application representation backfill, which permits V0 writers while V2 retains its fallback.

Include migration I/O, temporary space, source log retention/backlog, foreground latency/errors, and outstanding work in the rehearsal’s resource record. Correct answers and bounded serving impact are separate pass conditions.

## Rollback and rollforward limits

Application rollback is possible only while old code can interpret current data and its required schema still exists. Keeping bridge writes preserves one route; it does not make all transformations reversible. Code-only readers require writers that maintain the code: rolling the writer binary back to V0 alone would violate that rule. Restore the fallback before admitting those writes, or preserve the bridge and writer floor. A widening from `int` to `bigint` followed by an out-of-range value, or dropping uniqueness followed by duplicates, can make a schema revert fail under the documented Vitess contract. Treat newly accepted enum meanings similarly in the application model.

Retaining an old table is insufficient if it no longer receives all acknowledged writes. Check the reverse stream’s actual progress and constraints; Shopify’s resharding account shows a cross-shard ordering hazard. After the supported revert route closes, the options are a compatible forward repair or an explicitly scoped restore/replay procedure with a declared data-loss/reconciliation contract. Recreating a dropped column does not restore discarded values. No automated rollback, restore, or destructive action was executed here.
