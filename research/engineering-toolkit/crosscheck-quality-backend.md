# Independent backend crosscheck and failure-testing contract

Reviewed 2026-09-29 by the quality research lane. This review read both backend lane records, the four selected articles' main prose, and their current-contract crosschecks. No material contradiction remains in the backend synthesis. The conditions below must survive conversion into skills and evaluations.

## Backend findings

- **Operation identity:** [Stripe's historical article](https://stripe.com/blog/idempotency) motivates retrying uncertain operations under a stable identity. Its broad retry wording is not a provider-independent permission to retry every error forever. The [current API contract](https://docs.stripe.com/api/idempotent_requests) preserves the first executed response, including HTTP 500; validation and concurrent execution conflicts are different. Keys can be pruned after at least 24 hours, after which reuse can execute a new operation. Do not turn this into an exact 24-hour lifetime, durable deduplication forever, or permission to generate a fresh key after an ambiguous failure. The backend lane already records these qualifications.
- **Modular boundaries:** [Shopify's account](https://shopify.engineering/shopify-monolith) supports inspecting dependencies and change locality before standardizing interfaces. Its intermediate organizational choices are contextual. Our integration guardrail is to require evidence that an extracted boundary reduces coupling; neither a uniform wrapper nor an acyclic graph proves semantic independence. Dependency inversion does not automatically justify asynchronous messaging. The lane does not make those stronger claims.
- **Migration safety:** [GitHub's migration workflow](https://github.blog/enterprise-software/automation/automating-mysql-schema-migrations-with-github-actions-and-more/) supports recorded state, review, staged execution, and controlled database authority. Its availability wording must not become a no-lock guarantee. [gh-ost's documented default cut-over](https://github.com/github/gh-ost/blob/master/doc/cut-over.md) briefly blocks access and uses an atomic rename sequence; timeout or connection failure can release the attempt while leaving the original available. Atomic cut-over does not make the entire migration atomic or prove compatibility of rollback data. The historical orchestration code depends on unpublished company libraries and services.
- **Retry ownership:** [Uber's retry-storm mechanism](https://www.uber.com/us/en/blog/protecting-against-retry-storms/) depends on error provenance, participating layers, and fallback behavior when context is absent. Its simplified availability comparison assumes independent errors, which overload can violate. A downstream failure can also coincide with a separate upstream defect. Keep this a conditional mechanism, not a universal mesh requirement. The [gRPC guide](https://grpc.io/docs/guides/retry/) confirms transparent retries can exist without configured retry policy. Response-header commitment stops transport retries; it does not establish whether a business effect committed. Inventory the actual SDK, application, proxy, and transport behavior.

A reciprocal review found one overstrong assertion in `lanes/quality.json`: cached TLS certificates bypass autocert's new-certificate `HostPolicy`. Corrected its verification criterion to test cold-cache acquisition denial, with warm-cache endpoint rejection required only when a separate routing or host-access policy implements retirement. The existing Markdown limitation was already accurate. [Current autocert contract](https://pkg.go.dev/golang.org/x/crypto/acme/autocert#Manager)

## Reproducible failure-oriented testing

A random seed reproduces generated data only within its documented constraints. It does not independently reproduce a process scheduler, uncontrolled network responses, external state, or a changed generator. Tests should name the invariant, expose narrow synchronization points, retain a minimal failing history, and state which concurrency they control.

**TypeScript.** fast-check's `scheduleFunction` invokes the original function immediately and schedules only its returned promise's resolution. Gate before invocation to control arrival at a mocked service; separately control completion where the invariant requires it. Avoid a scheduled sequence that waits for a task the same scheduler cannot release until that sequence finishes. `waitIdle` does not control real network or external event sources. Use the current `waitNext`/`waitFor`/`waitIdle` APIs for compatible pinned releases. These are explicit limits of the [scheduler](https://fast-check.dev/docs/advanced/race-conditions/). Keep the seed, shrink path, scheduler report, and dependency version; command-based tests additionally need the command `replayPath` for direct minimal replay. Preserve a readable regression after fixing the defect. [Model replay](https://fast-check.dev/docs/advanced/model-based-testing/)

**Python.** Generate valid operation histories with Hypothesis and compare against a small explicit model. Its rule-based state machines check invariants after steps; this does not automatically enumerate asyncio or thread interleavings. Add explicit events/barriers to exercise the relevant schedule. Preconditions must not skip every interesting action. [Stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html) Reset databases, files, environment, and model state for each example; uncontrolled randomness and scheduling can make failures unreplayable. [Flaky failures](https://hypothesis.readthedocs.io/en/latest/tutorial/flaky.html) Retain the minimized concrete history as an ordinary regression or explicit example. The example database is useful but not a permanent compatible archive; opaque reproduction blobs are version-sensitive. [Failure replay](https://hypothesis.readthedocs.io/en/latest/tutorial/replaying-failures.html)

**Go.** Use explicit channel gates for the schedule and `testing/synctest` for contained timer/cancellation behavior. `Wait` means other bubble goroutines are durably blocked, not necessarily that the requested operation completed. Socket I/O, syscalls, and mutex acquisition are not durable blocking operations for fake-clock advancement. Avoid external goroutines/processes and real networking inside the bubble. Fake time is not exhaustive schedule exploration. [synctest contract](https://pkg.go.dev/testing/synctest) Stable `Test`/`Wait` require Go 1.25; older experimental examples have different APIs. [Release notes](https://go.dev/doc/go1.25#testing/synctest) Native fuzzing retains minimized failures in `testdata/fuzz`; retain that corpus and rerun it as ordinary regression tests. [Go fuzzing](https://go.dev/doc/security/fuzz/)

Run Go's race detector in addition to invariant checks. It finds data races on exercised paths, not every semantic concurrency error. A mutex around each read and write can still lose an update when the complete read-modify-write operation is unprotected. The detector also has platform/cgo requirements and overhead that must be recorded. [Race detector](https://go.dev/doc/articles/race_detector)

## Proposed equivalent backend evaluation

This is a repository-specific contract to implement after research, not a claim that the complete evaluation already ran.

| Scenario | Forced boundary | Required observation in all three languages |
| --- | --- | --- |
| Concurrent duplicates | Pause the first request after ownership acquisition; start its duplicate. | One committed effect per authorized operation identity; duplicate follows the documented in-progress/result behavior. |
| Lost response | Commit the effect, then discard the reply before the caller receives it. | Retry preserves identity and returns or reconciles the existing result without a second effect. |
| Payload mismatch | Reuse the identity with different validated payload. | Explicit mismatch, no second effect, no other principal's result disclosure. |
| Cancellation before commit | Cancel while waiting at a pre-commit gate. | The fixture's stated contract is met; owned resources close and cancelled children are joined. |
| Cancellation after commit | Cancel after the commit gate but before delivery. | Effect remains committed; caller uncertainty is represented and recovery uses the same identity. Cancellation is not reported as rollback. |
| Resource cleanup | Fail or cancel at each acquisition stage. | Every acquired resource is released once; no outstanding owned tasks remain after the documented shutdown bound. |
| Semantic race | Allow two reads of the same version before either write. | Both logical updates survive or one is explicitly rejected/retried under the chosen conflict contract. |

The fixture should expose a small operation API, an authorized identity plus payload fingerprint, an effect ledger, an ownership/result store, explicit clock/scheduling hooks, and a history of observed transitions. Assertions must cover the public contract, not just internal method call counts. Include malformed input before effects. Define cancellation ownership: request lifetime and durable operation lifetime can differ. This is an evaluation design choice, not a universal instruction to stop work after client disconnects.

Keep one shared scenario manifest and language-specific adapters. Record revision, exact runtime/dependencies, invocation, generated/accepted/skipped counts, fault point, schedule/history, observed invariant, and replay artifact. Require the retained case to fail the broken behavior and pass the correction. Reaching a time limit is incomplete evidence if the promised run budget did not finish; fast-check's legacy interruption settings can otherwise report success, and current releases provide a plugin failure option. Check the pinned API rather than silently copying deprecated configuration. [Runner parameters](https://fast-check.dev/docs/api/interfaces/Parameters/)

These in-memory fixtures demonstrate control flow and fault handling; they cannot establish a database's isolation, broker durability, cross-process deduplication, or a real provider's retention behavior. Adapter-level integration tests must separately exercise the deployed contract, including restart persistence and uncertain transaction completion when claimed.

## Observed feasibility and limits

The research machine reported Go 1.27.1 on darwin/arm64, Node 25.9.0, and Python 3.14.3. Hypothesis and fast-check were absent from the current project environment; their proposed properties were not executed. Documentation displayed Hypothesis 6.168.3, and fast-check documentation was current at access time; implementation must pin and validate chosen versions.

A temporary Go probe ran `go test -race -count=1 -v ./...`: two individually locked reads were forced to precede both individually locked writes. The two-increment invariant failed with an observed value of one and no data-race report; a control holding the lock through each update passed. The command exited 1 because the semantic assertion intentionally failed. This validates the need for both kinds of check; it is not a repository test pass. Only this scratch probe executed during this crosscheck; no final example or skill implementation was added.
