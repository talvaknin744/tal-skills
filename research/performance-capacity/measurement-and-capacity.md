# Measurement and capacity: primary-source findings

Research date: **2026-10-01**. Scope: source-backed requirements for `performance-diagnosis`, `load-testing`, `capacity-planning`, and `database-performance`. The requirements below are design deductions from the cited material, not measured results from this repository. No benchmark, live database, cluster experiment, or full-book reading was performed.

## Decisions for the skills

### Performance diagnosis

1. **Define useful work and the observation boundary.** Specify operation class, correctness, deadline, workload mix, and client-visible success. Track successes and failures with separate latency distributions; quick failures can otherwise make overall latency look better. Derived requirement: report correct, on-time completions per second alongside attempted load, timeouts, rejection, cancellation, and unfinished work. [Google SRE, Monitoring Distributed Systems: Four Golden Signals](https://sre.google/sre-book/monitoring-distributed-systems/).

2. **Ask resource questions before choosing tools.** Examine utilization, saturation, and errors for CPU, memory, storage, network, and constrained software resources. Low interval-average utilization can conceal bursts; finding one problem does not establish that it causes the user-visible symptom. Derived requirement: a resource map, explicit unmeasured resources, and a falsifiable bottleneck hypothesis with supporting request-path evidence. USE is an early triage method rather than a complete diagnosis. [Brendan Gregg, USE Method: Summary, Software Resources, Cloud Computing, Strategy](https://www.brendangregg.com/usemethod.html).

3. **Separate executing from waiting.** CPU profiles sample executing threads; off-CPU analysis examines waiting, including I/O, locks, and scheduler delays. Background idle threads can dominate an off-CPU profile, and scheduler wait may be included in an apparent blocked interval. Derived requirement: connect profiles to the slow operation and distinguish queue wait, runnable delay, useful execution, synchronization, dependency time, and allocation/GC where observable. Measure tracer overhead. [Gregg, Off-CPU Analysis: introduction, Overhead, Caveats](https://www.brendangregg.com/offcpuanalysis.html).

4. **Validate one intervention against the baseline.** Analyze the target, client, transport, and resource controls while a benchmark runs. A plausible result can be limited by a single-threaded generator, network, neighboring work, or unrealistic input. Derived requirement: preserve workload, limits, software/configuration versions, and warm/cold conditions; show the mechanism changed and compare useful work and latency, with variability and remaining uncertainty. A short test can establish a local improvement without establishing sustainable capacity. [Gregg, Active Benchmarking: Summary, Active Benchmarking, Problem Checklist](https://www.brendangregg.com/activebenchmarking.html).

### Load testing

| Evidence | Derived application requirement | Limit or counterexample |
| --- | --- | --- |
| Closed executors couple new iterations to prior completion; open executors decouple arrivals from completion. [k6: Open and closed models](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/) | Select the arrival model from production demand. Use independent arrivals when testing externally imposed demand; use closed populations when users actually wait before their next action. | A fixed-VU test can silently reduce demand as latency grows. A closed model is appropriate for a real closed population; neither model is universally correct. |
| Arrival-rate executors drop iterations when no VU is free. Early drops may mean inadequate allocation; later drops may reflect slower target iterations. [k6: Dropped iterations](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/) | Reconcile scheduled, started, dropped, interrupted, and completed iterations. Provision and observe the generator; investigate drops before accepting the offered-load claim. | A dropped iteration is work never started by the executor, not a server rejection or a sampled request latency. Drops alone do not identify the cause. |
| `http_req_duration` includes send, wait, and receive, excluding initial DNS/connection time; blocked/connecting/TLS are separate metrics. Iterations and HTTP requests are different counters. [k6: Built-in metrics](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/) | State metric units and timing boundary. Measure logical operations and retry attempts separately; count correctness with checks or business assertions. Preserve client elapsed time when claiming end-to-end latency. | One iteration can issue several requests. HTTP success classification and raw request count do not establish a correct business outcome. |
| Histograms permit distribution aggregation; averaging precomputed worker quantiles is statistically invalid. Quantiles carry estimation error. [Prometheus: Histograms and summaries](https://prometheus.io/docs/practices/histograms/) | Aggregate compatible distributions before computing fleet percentiles. Record window, operation/outcome population, sample count, and histogram resolution; prefer explicit SLO-threshold counts where available. | A precise-looking p99 can exceed the available resolution. Changes in bucket layouts or population can invalidate comparisons. |

Test representative workload mix, payload/data size, tenant/key skew, stateful correctness, retries, and connection behavior. Include warm and cold starts, ramps and impulses, sustained overload, dependency slowdown, capacity loss, and recovery after demand falls. Google's guidance ties breaking-point tests to capacity planning, warns that warm-up paths differ, and calls for correctness checks under load. Tests should run within committed resource limits. **Required result:** a reproducible workload and outcome report, actual delivered demand, target and generator saturation evidence, and clearly scoped capacity conclusions. [Google SRE, Addressing Cascading Failures: Capacity Planning; Planned Changes; Resource Limits; Testing for Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/).

### Capacity planning

Raw QPS is an incomplete capacity model because operation costs and workload mix change. Resource demand should be measured per class and dependency, with CPU, memory, I/O, network, concurrency, and storage considered as relevant. CPU can be useful when other resources have adequate provisioning, but that assumption is conditional. [Google SRE, Handling Overload: Pitfalls of Queries per Second](https://sre.google/sre-book/handling-overload/).

**Derived model:** for class `i`, arrival rate `λᵢ` in operations/second and CPU demand `Dᵢ` in CPU-seconds/operation imply aggregate demand `Σ λᵢDᵢ` in CPU-seconds/second. This is an accounting estimate, not a latency or scalability guarantee. Measure fan-out, retries, background/maintenance work, and expensive classes separately. Price capacity using **cost per correct, on-time useful operation** over an explicitly chosen window; report fixed, idle, storage, network, and failure-reserve costs included in that numerator.

For a stable boundary, Little's Law relates **mean** population `L`, admitted arrival rate `λ`, and **mean** time within that boundary `W`: `L = λW`. Units must match: operations/second × seconds = operations. For a queue-only boundary use queue wait and queued population; for a whole stage include service. Finite-capacity systems require effective arrivals that enter the system. A stationary model's long-run means need stability; finite-window accounting requires boundary/censoring treatment. The formula supplies neither a p99 prediction nor an optimal concurrency limit. [MIT 1.041, Queueing Models, Spring 2026: PDF pages 14–18 and 32](https://web.mit.edu/1.041/www/lectures/L8-queuing-models-2026sp.pdf).

Autoscaling reacts after observation and startup delays; nonserving instances can distort average utilization. Scaling the frontend may overload dependencies. The Workbook recommends spare capacity, bounded scaling, and capacity per failover location; it also illustrates shedding-induced errors being misread as cheap successful traffic. [Google SRE Workbook, Managing Load: Autoscaling; Combining Strategies](https://sre.google/workbook/managing-load/).

**Derived requirement:** produce a scenario table for ordinary peaks, growth/workload shifts, rollout/drain, replica or zone loss, cold replacements, retry amplification, and recovery. For each scenario give measured usable capacity, bottleneck/dependency limits, headroom, scaling lag, quota, routing/skew assumptions, and confidence. Count ready, routable capacity rather than provisioned replicas. Treat uniform replica multiplication as a hypothesis requiring evidence. The final recommendation needs scaling triggers, cost, and an explicit condition that would invalidate it.

### Database performance

| Evidence | Derived application requirement | Limit or counterexample |
| --- | --- | --- |
| PostgreSQL exposes active query state and waits independently; an active backend can be blocked. Cumulative counters lag, can reset, and are cached within a transaction. [PostgreSQL 18: Monitoring Statistics, §§27.2.1–3](https://www.postgresql.org/docs/18/monitoring-stats.html) | Align request latency, wait samples, blockers, I/O, and interval counter deltas; record settings, resets, and observation transaction boundaries. | A query marked active is not necessarily consuming CPU. A cumulative total or stale snapshot cannot establish an incident-window rate. |
| `pg_stat_statements` records calls, execution/planning totals, rows, buffers, temporary blocks, and WAL; some timing requires enabled collection. [PostgreSQL 18: pg_stat_statements, introduction and view](https://www.postgresql.org/docs/18/pgstatstatements.html) | Prioritize aggregate workload impact and latency-sensitive classes, not only the single slowest query. Distinguish disabled instrumentation from a measured zero. | Normalized statement aggregates can hide parameter skew and tails. Enabling the module can require restart; existing evidence can guide initial diagnosis. |
| Planner costs are arbitrary units; actual node times/rows are per loop. `EXPLAIN ANALYZE` executes the query, adds overhead, and excludes network delivery. [PostgreSQL 18: Using EXPLAIN, §§14.1.1–3](https://www.postgresql.org/docs/18/using-explain.html) | Capture representative parameters, data size/skew, estimates versus actuals, loops, buffers, and spill evidence. Keep plan analysis distinct from client/pool latency. Execute side-effecting analysis in an appropriate environment; rollback is not evidence that every external effect is reversible. | A sequential scan can be correct. Summing nested inclusive timings double-counts. A toy table, one warm run, or the fastest parameter is insufficient. |
| PgBouncer reports `cl_waiting`, server assignment wait in microseconds, and query/transaction times. Wait totals update on assignment. [PgBouncer: SHOW STATS and SHOW POOLS](https://www.pgbouncer.org/usage.html) | Instrument application pool acquisition separately; inspect pooler queues and PostgreSQL waits. Validate pool changes against database throughput and concurrent memory demand. | Assigned-client average wait omits clients still waiting. A larger pool is a hypothesis, not a universal fix; pooler observations are conditional on actually using PgBouncer. |
| `work_mem` applies per operation; multiple operations, sessions, hash multipliers, and maintenance workers multiply memory demand. [PostgreSQL 18: Resource Consumption, memory settings](https://www.postgresql.org/docs/18/runtime-config-resource.html) | Budget memory under the proposed concurrency and workload mix before raising sort/hash limits. Include maintenance and parallel work. | A per-query improvement can create system-level memory pressure. `work_mem` is not a global memory cap. |
| VACUUM supports space reuse, statistics/visibility maintenance, and wraparound protection; `VACUUM FULL` rewrites with extra space and an exclusive lock. Parent partition statistics may need explicit ANALYZE. [PostgreSQL 18: Routine Vacuuming, §§24.1.1–3](https://www.postgresql.org/docs/18/routine-vacuuming.html) | Inspect maintenance backlog, long transactions, statistics freshness, table/index growth, and workload interference before selecting query/index/maintenance changes. Validate read, write, storage, and rollout costs. | Ordinary vacuum usually reuses space rather than returning it to the OS. Disabling maintenance or rewriting a busy table is not a general performance repair. |

## Conditional runtime and container references

Load these branches only after inspecting the deployed runtime and limits.

- **Containers/Linux:** Kubernetes documents CPU throttling and reactive memory enforcement. Inspect effective requests/limits and runtime cgroups, not only host-average CPU. [Kubernetes: Resource Management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/). Linux v2 documents `cpu.max`, `cpu.stat` usage/throttling, pressure, and hierarchical `memory.events`; verify supported files and ancestor limits on the actual kernel. Metric counter differences and scope matter. [Kernel: cgroup v2 CPU and Memory](https://docs.kernel.org/admin-guide/cgroup-v2.html).
- **Go:** CPU, heap, block, and mutex profiles answer different questions, and profiling has overhead. [Go: Diagnostics, Profiling and Tracing](https://go.dev/doc/diagnostics). Allocation rate, live heap, and memory-limit choices affect GC work; `GOMEMLIMIT` is soft and too little memory can cause repeated collection with poor progress. Include non-Go runtime memory in the container budget. [Go: GC Guide, GOGC and Memory Limit](https://go.dev/doc/gc-guide).
- **Node:** event-loop delay histograms report nanoseconds. The current documentation exposes different sampling modes that should not be compared directly; use the deployed version's API and consistent sampling configuration. Event-loop delay is one mechanism signal, not full request latency. [Node: monitorEventLoopDelay](https://nodejs.org/api/perf_hooks.html#perf_hooksmonitoreventloopdelayoptions).
- **Python:** deterministic profilers attribute execution but are unsuitable as comparative benchmark timers; Python-level overhead can bias comparisons with C functions. Use profiling for attribution and an independent timing/load measurement for validation. [Python: The Python Profilers, introduction](https://docs.python.org/3.14/library/profile.html).
